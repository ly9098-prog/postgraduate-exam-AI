# 图片题目导入风险分析

> 风险分析对象：图片上传 → PaddleOCR → OCR 文本缓存 → ImportPipeline TXT 分支 → question_imports 审核 → 人工入库。
> 修订说明：根据 Auditor 审计，图片导入只保留“图片 OCR → raw_text → ImportPipeline TXT 分支 → question_imports 审核队列”一条主路径。

## 1. 风险总览

| 风险 | 等级 | 影响 | 第一版策略 |
|---|---:|---|---|
| 大图片上传 | P1 | 请求慢、内存高、真机失败 | 限制大小和尺寸，必要时压缩 |
| OCR 超时 | P1 | 用户等待过久、任务失败 | 后台任务、状态查询、超时失败可重试 |
| 中文识别准确率 | P2 | 题干/选项错字 | 原文展示 + 人工审核 |
| 数学公式识别 | P1 | 公式错识别影响题目正确性 | 明确低置信度，人工校正，不承诺 LaTeX 完整准确 |
| 表格识别 | P2 | 表格题结构丢失 | 第一版作为纯文本处理，不做表格结构化 |
| 服务器 CPU 占用 | P1 | 主 API 变慢 | 限制并发、缓存、必要时拆 worker |
| 并发问题 | P1 | 任务堆积、状态错乱 | pipeline_id 隔离、并发限流 |
| 存储成本 | P2 | 原图和缓存累积 | 临时保存、定期清理、不长期绑定原图 |
| 数据污染 | P0 | 未审核内容进入题库 | 必须经过 `question_imports` 和人工确认 |
| 现有流程回归 | P0 | PDF/Excel 导入被破坏 | 图片使用独立入口，不改现有入口行为 |

## 2. 大图片上传

### 风险描述

手机拍照图片可能达到 5-20MB，分辨率可超过 4000px。直接上传并 OCR 会带来：

- 小程序上传超时。
- FastAPI 读取文件占用内存。
- 图片解码占用 CPU/内存。
- PaddleOCR 推理时间显著增加。

### 触发条件

- 用户直接上传原始拍照图。
- 多图连续上传。
- 网络较差或服务端资源较低。

### 建议控制

1. 限制单图大小，例如第一版 5MB 或 8MB。
2. 限制最大边长，例如超过 2500px 先压缩。
3. 前端提示“建议裁剪到题目区域”。
4. 后端必须重新校验，不能只依赖前端。

### 验证

- 1MB 截图、5MB 拍照图、超限图片分别测试。
- 真机弱网测试上传失败提示。

## 3. OCR 超时

### 风险描述

PaddleOCR 首次加载模型慢，复杂图片识别也可能长时间占用 CPU。同步 HTTP 等待会导致用户体验差，也可能被网关超时中断。

### 触发条件

- PaddleOCR 首次初始化。
- 大图或复杂版面。
- 并发 OCR。
- CPU 资源不足。

### 建议控制

1. 图片 OCR 使用后台任务。
2. 前端通过状态接口轮询，状态字段直接对齐现有 pipeline 语义。
3. 设置单图 OCR 超时时间。
4. 超时任务标记失败并保留错误原因。
5. 第一版不拆独立 OCR worker。

### 验证

- 冷启动首次 OCR。
- 连续上传 5 张图。
- 人为模拟 OCR 超时，确认任务状态可结束。

## 4. 中文识别准确率

### 风险描述

PaddleOCR 对清晰印刷中文通常可用，但仍会出现：

- 相近字误识别。
- 标点丢失。
- 题号、选项符号识别错误。
- 分栏顺序错乱。

### 影响

- 切题失败。
- 选项错配。
- 答案行无法识别。
- 题干产生错字。

### 建议控制

1. OCR 原文可预览。
2. 解析结果必须人工审核。
3. 低置信度题目标记 warnings。
4. 前端提示用户上传清晰、正向、裁剪后的图片。

### 验证

- 清晰截图。
- 手机拍照。
- 斜拍图片。
- 带阴影图片。

## 5. 数学公式识别

### 风险描述

数学公式是本项目图片 OCR 的高风险点。PaddleOCR 主要识别文字，对复杂公式、上下标、分式、矩阵、积分符号、极限表达式不稳定。

### 影响

- 数学题题干错误。
- 答案或解析公式不可用。
- 后续 LaTeX 渲染异常。

### 建议控制

1. 第一版不承诺公式自动结构化。
2. OCR 结果按普通文本进入审核。
3. 数学题默认提示“请重点检查公式”。
4. 保留原图短期预览，便于人工对照。
5. 不让 AI 自动猜补关键公式后直接入库。

### 验证

- 分式、积分、矩阵、极限、上下标样例。
- 检查小程序渲染是否因异常符号崩溃。

## 6. 表格识别

### 风险描述

试卷和课本中可能存在表格题、数据结构表、真值表、矩阵排版。纯文本 OCR 容易丢失行列关系。

### 影响

- 题意缺失。
- 选项和表格内容混合。
- AI repair 可能错误补全。

### 建议控制

1. 第一版不做表格结构化识别。
2. OCR raw_text 保留换行但不保证列结构。
3. 表格题进入低置信度审核。
4. 后续如需求强烈，再设计表格专用 OCR。

### 验证

- 408 表格题。
- 英语阅读表格。
- 数学矩阵和表格混排。

## 7. 服务器 CPU 占用

### 风险描述

PaddleOCR 是 CPU/GPU 密集型任务。若运行在主 FastAPI 进程内，大量 OCR 会影响普通 API、刷题接口和 PDF 导入。

### 触发条件

- 多用户同时上传。
- 大图 OCR。
- OCR worker 数过高。

### 建议控制

1. `OCR_MAX_WORKERS` 保守设置。
2. 图片 OCR 单独并发限制。
3. OCR 结果缓存。
4. 记录耗时，观察 P95/P99。
5. 压测后再决定是否拆独立进程或服务。

### 验证

- OCR 并发 1、2、4 的耗时和 API 响应变化。
- OCR 运行时访问批次列表、题库列表。

## 8. 并发问题

### 风险描述

并发上传可能引发：

- 相同图片重复 OCR。
- pipeline 状态覆盖。
- 后台任务异常后状态悬挂。
- 多任务同时写入审核队列。

### 建议控制

1. 每个上传生成独立 `pipeline_id`。
2. 用图片 hash 做缓存键。
3. 状态更新必须按 pipeline_id 隔离。
4. 异常必须进入 terminal 状态：completed/failed。
5. 写入 `question_imports` 时保持现有事务边界。

### 验证

- 同一图片重复上传。
- 两张不同图片同时上传。
- OCR 成功但解析失败。
- 解析成功但写入审核失败。

## 9. 存储成本

### 风险描述

图片原图、压缩图、OCR JSON、日志如果不清理，会持续增长。

### 建议控制

1. 原图和压缩图默认短期临时保存，建议 7 天内清理。
2. OCR cache 设置过期策略，建议 30 天内清理或按存储上限淘汰。
3. 仅 `question_imports.raw_data` / `ai_metadata` 保存必要摘要、hash、错误码和 OCR 元数据，不塞入大型对象。
4. 不把 base64 图片写入数据库。
5. OCR 失败不进入审核队列，但保留任务错误状态和短期原图预览能力。

### 验证

- 连续导入 100 张图后检查存储目录大小。
- 删除过期任务后确认审核记录仍可正常显示必要信息。

## 10. 数据污染和流程绕过

### 风险描述

如果为了提升体验让 OCR/AI 结果直接写 `questions`，会违反项目核心约束，并可能污染正式题库。

### 必须遵守

```text
图片 OCR / AI repair / 自动解析
  → 只能写 question_imports(pending)
  → 必须人工审核
  → 审核通过后才写 questions
```

### 验证

- 图片上传完成但未审核前，`questions` 表无新增。
- 拒绝题目不入库。
- 低置信度和缺答案题不可批量静默入库。

## 11. 现有流程回归

### 风险描述

图片导入如果直接改造 `/import/upload`、`_parse_pdf()` 或 PDF OCR 路径，可能破坏已经可用的 Excel/PDF 导入。

### 建议控制

1. 图片入口独立，不修改 `/import/upload` 的 Excel/PDF 分支。
2. PDF 入口白名单和解析逻辑保持原行为。
3. 复用底层 OCR 能力时，不改变 `ocr_pages()` 现有签名。
4. 以新增单图 OCR 包装函数为主，不改旧 PDF OCR 主逻辑。
5. 图片 OCR 后只包装为 TXT 输入并进入 `ImportPipeline` TXT 分支。

### 验证

- Excel 模板导入。
- 文本型 PDF 导入。
- 扫描版 PDF 现有行为。
- 图片导入失败不影响批次列表和审核页。
