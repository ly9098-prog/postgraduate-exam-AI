## 第一部分：优先级合理性评审

### P0-1：旧版 `ocr_correction.py` 纠错路径清理

| 维度 | 评价 |
|------|------|
| **定级** | P0 合理。两条并行纠错路径（旧版 `ocr_correction.py` + 新版 `ocr_fix/router.py`）是当前管线的核心架构债务。两者由不同配置开关控制（`enable_ai_correction` vs `enable_ai_repair`），prompt 不同、处理逻辑不同、可能导致同一批 OCR 文本输出不同结果。这是重复 LLM 调用叠加结果不一致的组合风险。 |
| **工作量** | 2-3 天合理。`ocr_correction.py` 548 行，包含噪声检测、结构异常检测、质量分级、AI 纠错调用、敏感内容过滤。迁移到 `ocr_fix/router` 需要：适配敏感内容过滤能力、验证路由降级链行为一致、回归测试覆盖。3 天偏保守但可接受。 |
| **依赖** | 前置条件：确认 `ocr_fix/router` 已具备完整的功能等价（特别是敏感内容过滤，见第二部分 2.3 分析）。无硬依赖，可独立执行。 |

### P0-2：`clean_ocr_text` 和字符映射逻辑归并

| 维度 | 评价 |
|------|------|
| **定级** | P0 合理。三处重复（`services/ocr_service.py`、`text_normalizer.py`、`question_splitter.py`），不同步意味着修复了一处其他两处还是坏的。历史 CJK 字符丢失 bug 就是典型后果。字符替换表差异（8→B、0→D、l→1 等）在不同文件中有不同版本，导致同一文本经过不同路径得到不同结果。 |
| **工作量** | 1-2 天合理。主要是梳理三处逻辑差异、制定统一映射表、替换引用。 |
| **依赖** | 无硬依赖，可独立执行。但建议在 P0-1 之前或并行执行，因为旧版清理后会更明确归并目标。 |

### P1-1：`pipeline_orchestrator.py` 拆分为 `pipeline_stages/`

| 维度 | 评价 |
|------|------|
| **定级** | P1 合理但不是最高优先级。3550 行超级类的可维护性问题是真实存在的。但注意：生命周期审计（`ocr-pipeline-lifecycle-audit.md`）指出的 **P0 级别内存问题**（PDF bytes 全程驻留、EXERCISE_DETECTION 双 OCR、`_pipeline_store` 大字段积累）与这个结构拆分是不同维度的问题。结构拆分改善可维护性，但**不解决内存崩溃风险**。应将生命周期审计的 P0 内存任务作为独立 P0 任务补充（见第二部分 1.1）。 |
| **工作量** | 3-5 天合理。16 个阶段拆分为独立文件，加上 `pipeline_state.py` 和 `pipeline_api.py`。注意：如果同时采纳生命周期审计的流式改造（方案 B），则此拆分方式需配合流式架构重新设计，工作量可能上升到 5-8 天。 |

## 第二部分：遗漏检查

### 1. 架构问题遗漏

#### 1.1 生命周期审计的三个 P0 未纳入（**最严重的遗漏**）

生命周期审计（`ocr-pipeline-lifecycle-audit.md`）第 9 章明确列出了三个 P0 任务，但在 6.4 中完全缺失：

| 遗漏任务 | 原定级 | 描述 | 建议补入 |
|----------|--------|------|---------|
| **PDF bytes 落盘释放** | P0（生命周期） | `_run_pipeline_with_db` 持 `file_content: bytes`（100-400 MB）贯穿整个流程，extract 后不释放。生命周期审计排名第 1 的大对象。 | **P0** |
| **消除 EXERCISE_DETECTION 双 OCR** | P0（生命周期） | 同一 PDF 在 lightweight 阶段和全量 OCR 阶段各扫一次，工作量翻倍。WSL 下 OOM 风险叠加。 | **P0** |
| **`_pipeline_store` 剥大字段** | P0（生命周期） | result.diagnostics 含 raw_questions_preview + ocr_correction.corrections，每条 0.5-3 MB，500 条累计 0.25-1.5 GB，24h TTL。 | **P0** |

**理由**：这三个问题直接影响系统能否稳定处理 400 页以上 PDF，是阻塞级别的性能/稳定性缺陷，优先级应高于结构拆分。

#### 1.2 pipeline_orchestrator.py 拆分粒度建议

6.4 中仅笼统地写「按阶段拆分为 pipeline_stages/ 目录」。生命周期审计给出了更细粒度的设计：

- 建议拆分出：`pipeline_state.py`（状态管理）、`pipeline_api.py`（公共 API）、每个阶段独立文件（`_run_extract.py`、`_run_ocr_correction.py` 等）
- 生命周期审计的方案 B（流式架构）更进一步：改为 region 分片 + 两阶段执行（预处理 → 批后处理）

建议在 6.4 的拆分任务中补充：
- 明确 state/data 的生命周期管理作为拆分的一部分（当前 data dict 持有所有阶段输出直到流程结束）
- 确认是否与流式架构（方案 B）兼容，或者先做纯结构拆分再做流式改造

#### 1.3 生命周期审计的其他 P1-P2 遗漏

| 遗漏任务 | 原定级 | 建议 |
|----------|--------|------|
| **stage 间清理 data 大字段** | P1（生命周期） | `raw_blocks` / `normalized_blocks` / `raw_questions` 在 stage 完成后可以 pop。可与结构拆分合并执行。建议补入 P1。 |
| **review 阶段分批 commit** | P1（生命周期） | 当前单事务包住全 batch（最坏 500+ INSERT），任意一题失败全回滚。每 50 题 commit 一次，失败粒度变小。建议补入 P1。 |

### 2. LLM 问题遗漏

#### 2.1 旧版路径清理已覆盖

旧版 `ocr_correction.py` 清理已作为 P0-1 纳入。内联 VL 代码（`is_vl` 分支）和 DeepSeek 纠错调用都会在这一任务中被处理。无遗漏。

#### 2.2 OCR 纠错指标追踪（能力成熟度审计 P0）

能力成熟度审计（`ocr-capability-maturity-audit.md`）将「OCR 纠错指标追踪」列为 **P0**：
> 当前无任何定量评估纠错效果，无法判断纠错是在改善还是破坏。

6.4 中的「添加 diff 记录」是此任务的前置条件，但不等同于完整的指标追踪。建议在 6.4 中：
- 将「OCR 纠错指标追踪」作为独立任务补入 **P1**
- 或扩展「添加 diff 记录」为「添加 diff 记录 + 纠错指标追踪」，工作量从 1-2 天提升到 2-3 天

#### 2.3 敏感内容过滤移植（能力成熟度审计 P1）

能力成熟度审计指出：旧版 `ocr_correction.py` 的 `_filter_sensitive()`（电话/邮箱/广告过滤）在新 `ocr_fix/router` 路径中未被调用。这是一个数据合规风险。

建议：在 P0-1（旧版清理）的任务描述中明确**将敏感内容过滤移植到新版路由**。目前 P0-1 只写了「清理旧版，统一到新版」，没有明确指出这是一个功能移植（而非删除）任务。

### 3. 幻觉防护遗漏

审计报告 3.5 节列出了三个缺失的保护措施，6.4 只覆盖了一个：

| 保护措施 | 是否在 6.4 | 状态 |
|----------|-----------|------|
| AI 纠错→修复之间的 diff 对比 | 已纳入（P1-3） | 需升级为 P0 |
| `complete_import`→`enrich_import` 串联的版本回退机制 | **遗漏** | **建议补入 P1** |
| 代码场景的语义等价性检查 | **遗漏** | **建议补入 P2** |

说明：
- `complete→enrich` 串联的版本回退机制：先让 AI 补全缺失字段，再让 AI 丰富知识点。如果补全阶段产生幻觉（填了错误的答案），丰富阶段会基于幻觉答案分析知识点。需要版本回退机制允许在发现 enrich 基于错误输入后回退到 complete 前的状态。
- 代码场景语义等价性检查：C 代码 OCR 识别率低 → 纠错可能改写代码逻辑 → 修复阶段进一步改变代码。需要检查纠错后的代码逻辑是否与原文语义等价。

### 4. 性能优化遗漏

#### 4.1 AI 修复的并行化状态

审计 6.4 只提到了「AI 补全并行化」（P1-4）。但审计 5.2 节还指出：
- `ai_repair` 在批量模式下已使用并发（concurrency=3），但单题回退是串行的
- `similarity_matcher` 全题库一次性加载（生命周期审计 P2）

这些相比 AI 补全并行化的收益小，不补入也可以接受。

#### 4.2 similarity_matcher 题库 LRU

生命周期审计列出「similarity_matcher 题库 LRU + 上限」为 P3，6.4 未包含。这个级别不补入合理。

### 5. 数据一致性 / 错误恢复 / 幂等性遗漏

#### 5.1 断点恢复完全缺失

生命周期审计 §8 的断点恢复方案——包括 `import_batches` + `import_regions` 两张表、region 级 checkpoint——在 6.4 中完全未提及。

这是一个严重遗漏。当前状态：
- OCR 中途崩溃：完全丢失进度，必须重头再来
- 第 287 页失败：标记 failed，用户重传
- 无任何持久化中间状态

建议补入 **P1**（最小子集：region 级 checkpoint，不写 OCR 中间 jsonl）。

#### 5.2 review 阶段分批 commit（已在上文 1.3 提及）

#### 5.3 raw_data 字段瘦身

生命周期审计 7.2 建议 `raw_data` 剥掉 `raw_text`、`warnings`、`similarity_suggestion`，单行体积下降 50%+。这是一个 database 级别的优化，建议补入 P2。

### 6. 测试遗漏（**最容易被忽视的遗漏**）

6.4 的改造优先级表中 **完全没有测试相关的任务**。但多个审计文档同时指出了测试体系的严重问题：

| 来源 | 问题 | 严重性 |
|------|------|--------|
| 真实案例回归审计 | 现有 11 个回归 case 全部使用合成文本，`--baseline` 模式生成 expected（同义反复测试），5 张真实图片全部 FAIL 但测试全部 PASS | **P0** |
| 真实案例回归审计 | 回归覆盖率仅 21/100，关键场景（两栏排版、代码指针乱码、水印污染）零覆盖 | P1 |
| 能力成熟度审计 | OCR 纠错效果无定量评估，纠错可能实际上在破坏数据 | P0 |
| 审计报告附录 | 列出超过 20 个测试文件，但没有一个测试能检测「两栏串行」或「选项错序」 | P1 |

**建议补充的测试任务：**

| 任务 | 优先级 | 工作量 | 理由 |
|------|--------|--------|------|
| 将 5 张真实图片（`success_case`、`faulty_case_1~3`、`watermark_fail_case`）纳入回归集，人工标注 ground truth | **P0** | 1 天 | 核心问题：现有回归体系是「同义反复」，5/5 真实图片 FAIL 但测试全部 PASS。不建真实基线就无法衡量改造效果。 |
| 修复回归测试 runner 的 `--baseline` 模式，禁止用管道输出作为 expected | P1 | 0.5 天 | 防止后续新增 case 继续产生同义反复测试 |
| 建立改造前后的回归对比基准 | P1 | 0.5 天 | 在 P0-1、P0-2 等改造完成后，自动对比改造是否引入回归 |

## 第三部分：关联风险检查

### 3.1 与生命周期审计的冲突和关联

| 关联点 | 分析 |
|--------|------|
| **pipeline_orchestrator.py 拆分 vs 流式改造** | 6.4 建议「按阶段拆分为 pipeline_stages/ 目录」，生命周期审计建议「方案 B：双阶段流式架构」。两者不是互斥的：先做结构拆分（当前阶段），再做流式改造（下一阶段）。但如果最终目标是流式，结构拆分时应预留流式接口（例如让每个 stage 的输入输出更独立）。**风险**：先按纯线性结构拆分，后续流式改造时要重新调整，造成重复工作。建议在结构拆分任务中明确「为流式预留接口」的设计约束。 |
| **P0 内存任务缺失** | 生命周期审计的 3 个 P0 内存任务（PDF bytes 释放、双 OCR 消除、store 瘦身）在 6.4 中完全未提及。这些任务与 6.4 的现有任务不冲突，可以直接补充。**最大风险**：如果只做 6.4 的改造而不做生命周期审计的 P0，大 PDF 崩溃问题无法解决。 |
| **pipeline_state 设计** | 生命周期审计建议新增 `pipeline_state.py` 管理 data dict 生命周期。这个提议应该在 6.4 的结构拆分任务中反映出来。 |

|--------|------|
| **无直接冲突** | 能力成熟度审计的 P0 建议（跨图片题目合并、纠错指标追踪）在 6.4 中未覆盖，但两者处于不同层面——6.4 是整改现有管线，能力成熟度是新增能力。建议在 6.4 补入「纠错指标追踪」（见第二部分 2.2），跨图片合则可单独规划。 |
| **表格结构化** | 能力成熟度审计将表格解析标注为弱项（5% 完成度），但考研场景表格占比低，6.4 未覆盖合理。 |

### 3.4 与图片导入审计的冲突和关联

| 关联点 | 分析 |
|--------|------|
| **无冲突** | 图片导入审计针对的是新增图片导入功能特性，与 6.4（现有管线改造）是不同方向的规划。两者可以独立推进。 |
| **潜在重叠** | 如果图片导入要复用 `ImportPipeline`，那么 6.4 的管线改造成果（特别是 `ocr_fix/router` 统一路径、OCR 缓存）会使图片导入受益。 |

## 总结

6.4 节给出的改造优先级总体上逻辑自洽、定性合理，但存在以下问题：

1. **重大遗漏**：生命周期审计的 3 个 P0 内存任务完全缺失（PDF bytes 释放、双 OCR 消除、store 瘦身），是当前管线最紧迫的性能/稳定性缺陷。
2. **定级偏低**：「AI 纠错→修复 diff 记录」应升级为 P0，而非 P1。
3. **测试体系空白**：全部改造任务中无测试相关条目，但多个审计文档同时指出回归测试存在「同义反复」的严重缺陷，5/5 真实图片 FAIL 但测试全部 PASS。
4. **幻觉防护不完整**：只覆盖了 diff 对比，遗漏了 `complete→enrich` 版本回退和代码语义等价性检查。
5. **断点恢复缺失**：当前无任何中间状态持久化，OCR 中途崩溃完全丢失进度。
6. **与生命周期审计的潜在冲突**：纯线性结构拆分与流式架构改造的关系未明确，可能导致重复工作。

推荐的补救方案是：在 6.4 的 10 个任务基础上，补充约 12 个遗漏任务，并采用三阶段执行路线——第一阶段解决内存崩溃和回归基线，第二阶段优化结构和幻觉防护，第三阶段补齐性能和度量体系。
