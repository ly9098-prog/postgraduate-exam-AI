请直接检查并修改当前微信小程序项目，修复 `pages/pomodoro` 自由计时可以无限运行的问题。

自由计时单次上限设为 **5 小时**。达到 5 小时后，如果用户仍未手动结束，程序必须自动结束本次自由计时，并按照正常手动结束流程保存一条完整计时记录。

不要只给修改建议，需要实际修改代码、补充回归测试并运行测试。

# 一、目标行为

自由计时最大时长固定为：

```js
const FREE_TIMER_MAX_SECONDS = 5 * 60 * 60; // 18000 秒
```

或使用毫秒常量：

```js
const FREE_TIMER_MAX_MS = 5 * 60 * 60 * 1000; // 18000000 毫秒
```

要求：

1. 自由计时达到 `05:00:00` 后立即停止。
2. 不允许继续增长到 `05:00:01`。
3. 自动结束时记录的有效时长固定为 5 小时。
4. 自动结束必须调用与“确认结束”相同的保存流程。
5. 不能只停止界面定时器而不保存记录。
6. 不能保存两条重复记录。
7. 番茄钟模式不受该限制影响。
8. 用户在 5 小时前手动结束时，保持原有流程。
9. 用户暂停自由计时时，暂停时间不计入 5 小时。
10. 用户恢复计时后，从已有有效时长继续累计。
11. 页面进入后台、锁屏或定时器被系统延迟时，仍需通过真实时间差判断是否达到上限。
12. 页面重新显示时，如果实际有效时长已经达到上限，应立即自动结束并保存。

# 三、计时必须基于真实时间差

不要简单依赖：

```js
setInterval(() => {
  seconds += 1;
}, 1000);
```

因为小程序切到后台、锁屏、系统节流或卡顿时，`setInterval` 不会准确每秒执行。

应基于：

```js
Date.now()
```

计算有效时长。

建议维护以下非响应式状态，具体命名遵循现有代码：

```js
this._freeTimerStartedAt
this._freeTimerAccumulatedMs
this._freeTimerInterval
this._freeTimerRunning
this._freeTimerFinalizing
this._freeTimerAutoFinished
```

有效时长计算建议：

```js
function getFreeTimerElapsedMs() {
  const accumulated = this._freeTimerAccumulatedMs || 0;

  if (!this._freeTimerRunning || !this._freeTimerStartedAt) {
    return accumulated;
  }

  return accumulated + Math.max(0, Date.now() - this._freeTimerStartedAt);
}
```

暂停时：

1. 将本段运行时间累加到 `_freeTimerAccumulatedMs`；
2. 清空 `_freeTimerStartedAt`；
3. 停止 interval；
4. 标记为暂停；
5. 暂停期间不能继续消耗 5 小时额度。

恢复时：

1. 保留此前累计时长；
2. 把 `_freeTimerStartedAt` 设置为当前 `Date.now()`；
3. 重新启动界面刷新 interval；
4. 达到剩余上限后自动结束。

# 四、5 小时上限检测

新增统一方法，例如：

```js
_checkFreeTimerLimit()
```

或：

```js
_syncFreeTimerState()
```

它负责：

1. 计算当前真实有效时长；
2. 将显示时长限制在最大值内；
3. 判断是否达到 5 小时；
4. 达到时触发自动结束；
5. 未达到时更新页面显示。

示例逻辑：

```js
const elapsedMs = this._getFreeTimerElapsedMs();
const cappedMs = Math.min(elapsedMs, FREE_TIMER_MAX_MS);

this._updateTimerDisplay(cappedMs);

if (elapsedMs >= FREE_TIMER_MAX_MS) {
  this._autoFinishFreeTimer();
}
```

注意：

- 页面显示不能短暂出现超过 5 小时的值。
- 自动保存的时长必须使用 `FREE_TIMER_MAX_MS`，不能使用已经漂移到 5 小时以上的原始值。
- 上限判断使用 `>=`，不能只判断 `===`。
- 所有计算必须防止负数、NaN 和非法时间戳。

# 五、自动结束流程

新增职责明确的方法，例如：

```js
_autoFinishFreeTimer()
```

要求：

1. 必须有防重入保护。
2. 立即停止计时。
3. 清理 interval 和其他定时任务。
4. 将最终有效时长固定为 5 小时。
5. 关闭暂停状态。
6. 不弹出“结束自由计时？”二次确认弹窗。
7. 调用正常保存记录的公共方法。
8. 保存成功后进入与手动结束相同的完成状态。
9. 更新番茄数、累计分钟或统计数据时，沿用现有逻辑。
10. 不允许在自动结束后再次点击按钮生成第二条记录。

建议将手动结束和自动结束都收敛到同一个底层方法，例如：

```js
_finalizeFreeTimer({
  reason: 'manual' | 'max-duration',
  durationMs,
  skipConfirm: true | false,
})
```

或等价结构。

不要复制两份保存接口代码。

自动结束原因可以只在前端内部使用，不要求修改后端接口。除非现有接口本身已有 `reason` 字段，否则不要擅自增加后端参数。

# 六、防止重复保存

重点处理以下竞态：

1. 计时刷新 interval 发现达到 5 小时；
2. `onShow` 同时发现达到 5 小时；
3. 用户恰好点击“确认结束”；
4. 自动保存请求尚未结束；
5. 用户快速重复点击结束按钮；
6. 请求回调和页面生命周期并发触发。

必须通过实例状态阻止重复结束，例如：

```js
if (this._freeTimerFinalizing) return;
this._freeTimerFinalizing = true;
```

保存成功后保持本次 session 已结束。

保存失败时：

- 不得生成重复记录；
- 页面不能恢复为仍在无限计时；
- 保留待重试状态或提供明确失败提示；
- 再次重试时仍以 5 小时为最终时长；
- 不允许因失败继续累计成 5 小时以上。

如项目已有请求防重、提交锁或 session id，优先复用。

# 七、页面后台、锁屏和重新进入

## `onHide`

自由计时正在运行时：

- 不要把“进入后台”误判为暂停；
- 保存足够的真实时间状态；
- 可以清理仅用于界面刷新显示的 interval；
- 不能清空开始时间。

## `onShow`

页面重新显示时：

1. 重新计算真实有效时长；
2. 如果达到或超过 5 小时，立即自动结束并保存；
3. 如果未达到上限且仍处于运行状态，恢复界面刷新 interval；
4. 如果原本处于暂停状态，不得自行恢复计时。

## `onUnload`

清理 interval，避免内存泄漏。

但不要因为页面卸载就误保存一条未结束记录，除非项目现有业务本来就会这样处理。

# 八、应用被系统回收或用户重新打开

检查当前自由计时是否已经使用本地存储保存运行状态。

如果已有持久化机制，扩展现有结构，确保至少保存：

```js
{
  mode: 'free',
  running: true,
  startedAt: 绝对时间戳,
  accumulatedMs: 已累计有效毫秒,
  paused: false
}
```

恢复时：

1. 读取旧 session；
2. 根据绝对时间戳重新计算有效时长；
3. 如果达到 5 小时，立即自动结束；
4. 最终记录时长固定为 5 小时；
5. 自动结束完成后清理旧 session。

如果项目当前完全没有计时恢复机制，不要求大范围重构整个应用，但至少确保：

- 页面 `onHide` / `onShow`；
- 锁屏；
- 小程序短时间切后台；

能够正确触发 5 小时限制。

若实现持久化，请复用项目已有 storage key 和 session 数据结构，不要另建多个互相冲突的 key。

# 九、显示和交互

自由计时显示应支持至少：

```text
00:00:00
04:59:59
05:00:00
```

达到上限后：

- 页面不再继续刷新；
- 暂停、继续和结束按钮不能继续操作旧 session；
- 不显示 `05:00:01`；
- 不出现负数或回到 `00:00:00`；
- 自动结束过程中可以显示现有 loading 状态；
- 保存成功后沿用现有结束反馈。

建议在自动结束后提示：

```text
自由计时已达到 5 小时上限，已自动结束并记录。
```

优先复用项目现有 toast 或提示组件。

该提示不能阻塞保存流程。

# 十、时长单位和记录准确性

先确认保存接口使用的是：

- 秒；
- 分钟；
- 毫秒；
- 开始、结束时间戳；

不要自行假设。

自动结束记录必须符合现有接口单位。

例如接口需要秒时：

```js
duration: 18000
```

接口需要分钟时：

```js
duration: 300
```

接口需要时间戳时：

- 开始时间沿用真实开始时间；
- 结束时间根据有效计时规则生成；
- 暂停时间不能算入有效时长。

如果接口只支持整数分钟，使用项目现有规则取整，不能另设一套不同的舍入方式。

记录在 `pages/pomodoro-stats` 中应正确显示为：

```text
5时0分
```

不要出现：

```text
300分0秒
5时0分1秒
```

但不要在本任务中重复重构统计页面已有格式化逻辑，除非确实发现它无法正确展示 5 小时记录。

请新增 Node 回归测试，例如：

- `clearInterval`

至少覆盖以下场景。

## 基础上限

1. 最大时长常量严格等于 5 小时：
   - `18000` 秒；
   - 或 `18000000` 毫秒。
2. 4小时59分59秒不会自动结束。
3. 正好 5 小时时会自动结束。
4. 超过 5 小时时也会自动结束。
5. 最终保存时长被限制为 5 小时。
6. 页面显示不会超过 `05:00:00`。

## 防重复

1. interval 连续触发多次，只保存一次。
2. `onShow` 与 interval 同时触发，只保存一次。
3. 用户手动结束与自动结束同时触发，只保存一次。
4. 保存请求进行期间，重复调用不会发起第二个请求。

## 暂停和恢复

1. 暂停期间不累计时长。
2. 恢复后从原累计时间继续。
3. 累计 4 小时、暂停 2 小时、再运行 1 小时后自动结束。
4. 暂停在 4小时59分59秒时，不应自动结束。
5. 恢复并运行 1 秒后自动结束。

## 生命周期

1. 页面隐藏后 interval 被安全处理。
2. 页面重新显示时通过 `Date.now()` 补算。
3. 切后台前 4小时59分50秒，后台经过 20 秒后返回，应立即自动结束。
4. 原本暂停状态下从后台返回，不应自动恢复。
5. `onUnload` 清理 interval。

## 手动结束回归

1. 5 小时前手动结束仍使用真实时长。
2. 手动结束仍显示原有确认弹窗。
3. 点击“继续计时”不会结束或保存。
4. 点击“确认结束”只保存一次。
5. 自动达到上限时不显示确认弹窗。

## 模式隔离

1. 番茄钟模式不会因 5 小时常量被提前或自动结束。
2. 只有自由计时模式应用该上限。
3. 已完成的旧记录不受影响。

## 异常处理

1. 保存失败后计时不会继续超过 5 小时。
2. 保存失败重试仍固定保存 5 小时。
3. 非法累计时长、负数或 NaN 会安全归零或回退。
4. 无效开始时间戳不会造成无限计时或重复保存。
