# ================================================== 三、审计 setData 性能

微信小程序的主要性能风险之一是频繁或大范围 `setData`。

请全局检查：

```text
setData(
this.setData(
```

重点检查 quiz-runner 和使用页面。

需要识别以下问题：

### 3.1 大对象或大数组重复下发

检查是否在每次点击多空选项时下发：

```js
currentQuestion
questions
_questionImages
_renderModel
_blankOptionGroups
完整题目列表
完整答案表
```

如果一次点击只改变当前空的一个选项，不应重新下发整道题或整个 questions 数组。

优先使用精确路径，例如：

```js
_blankOptionGroups[0].options
answersByQuestion[questionKey]
```

但不能为了精确更新制造大量难维护的路径拼接。

### 3.2 高频重复 setData

检查一次点击是否连续调用多次 `setData`，例如：

```text
组件乐观更新一次
页面更新答案一次
observer 再更新一次
_showQuestion 再更新一次
```

要求：

- 统计一次多空选项点击触发的 setData 次数。
- 明确每次 setData 的数据字段。
- 合并可安全合并的更新。
- 避免同一个状态在组件和页面被重复重建。

### 3.3 无变化数据仍然下发

检查用户点击已经选中的选项时，是否仍然：

- 重建所有选项
- 重新计算图片
- 重新计算题干模型
- 再次触发父页面更新
- 写入缓存

如果新值与旧值相同，应根据产品规则提前返回，避免无效刷新。

### 3.4 深拷贝造成阻塞

全局搜索：

```text
JSON.parse(JSON.stringify(
structuredClone
deepClone
cloneDeep
```

重点检查点击选项、切题、加载图片和 observer 中是否对大对象深拷贝。

禁止在高频交互路径中使用：

```js
JSON.parse(JSON.stringify(question))
```

如果仅修改一层答案或一个选项组，应使用受控的浅拷贝。

# ================================================== 四、审计 observer 和重复计算

检查 quiz-runner 中所有：

```text
observers
observer
```

重点检查 `currentQuestion`、答案、mode 等属性变化。

需要确认：

1. observer 是否在一次点击中被多次触发。
2. observer 是否每次都重新执行：
   - 题干解析
   - 图片 URL 提取
   - 富文本图片提取
   - 所有选项组 enrichment
   - JSON 解析
3. observer 内部是否调用会再次改变 observer 依赖字段的 `setData`。
4. 是否存在循环更新：
   - 父页面更新 currentQuestion
   - 子组件 observer 触发
   - 子组件 triggerEvent
   - 父页面再次更新
5. observer 是否用旧答案覆盖点击后的新答案。
6. 无关字段变化时是否也重建整个渲染模型。

要求：

- 将昂贵计算限制在真正相关的输入变化时执行。
- 多空选项点击时不得重新解析题干和图片。
- 图片变化时不得重置多空题选中状态。
- 当前答案变化时，只重新计算选项选择状态。
- 当前题变化时，才重新构建题干、图片和完整选项结构。

如果当前 observer 过于宽泛，请进行小范围职责拆分，但不要重写整个组件架构。

# ================================================== 五、审计多空选择题点击路径

追踪一次点击的完整调用链：

```text
WXML 点击
→ quiz-runner 点击函数
→ 本地状态更新
→ triggerEvent
→ 页面 selectBlankOption
→ 页面答案更新
→ currentQuestion/answer 属性变化
→ quiz-runner observer
→ WXML diff
```

检查以下风险：

### 5.1 同一次点击重复处理

确认是否同时存在：

- `bindtap`
- `catchtap`
- 子元素点击
- 父元素点击
- touchend 处理
- swiper 手势处理

导致一次点击被执行两次。

### 5.2 点击触发切题手势

检查：

```text
touchstart
touchmove
touchend
swipe
```

确认点击选项时不会同时进入横滑切题逻辑。

手势判断应有明确移动阈值，不能只要触摸结束就切题。

### 5.3 全量重建选项组

一次点击只改变当前空的选择状态。

不要在点击时重复执行：

```text
全部 blank groups 标准化
全部选项重新生成 key
图片重新提取
题干重新解析
整题重新 enrich
```

### 5.4 key 不稳定导致节点重建

检查 WXML 中：

```text
wx:key
```

以及 adapter 生成的 `_key`。

要求：

- `_key` 不得包含 `_selected`。
- `_key` 不得随点击变化。
- `_key` 不得依赖当前时间、随机数或数组序列化。
- 选中某个选项时应复用原节点，而不是销毁并重建整组选项。
- 不允许同一组中出现重复 key。

### 6.1 同步缓存写入

如果每次点击选项都会调用：

```js
wx.setStorageSync(...)
```

可能阻塞小程序主线程。

请检查能否改为：

- 内存中立即更新
- 使用异步 `wx.setStorage`
- 合理防抖后批量持久化
- 页面隐藏或切题时兜底持久化

但必须保证异常退出时答案丢失风险可控。

不要为了性能完全取消答题缓存。

### 6.2 大 JSON 序列化

检查是否每次点击都序列化完整题目列表或完整 answerMap。

如存在，应只持久化必要字段，或使用合适的节流/防抖。

### 6.3 scroll/touchmove 中 setData

scroll 和 touchmove 中不得无节制调用 setData。

如必须更新 UI：

- 使用阈值判断
- 只有状态发生变化时才 setData
- 使用合理节流
- 不要每一帧下发位置数据

# ================================================== 七、审计图片相关性能

检查图片展示更新是否引入以下问题：

### 7.1 点击选项导致图片重新加载

多空选项点击时：

- `_questionImages` 不应被重新创建成全新数组，除非题目变化。
- 图片节点 key 不应变化。
- 图片不应闪烁或重复触发 `bindload`。
- 不应重新请求同一张图片。

### 7.2 图片 bindload 高频 setData

检查 `onQuestionImageLoad` 是否：

- 每张图片加载后重建整个图片数组
- 更新完整 currentQuestion
- 更新所有图片尺寸
- 触发题目重新排版

应只记录必要尺寸或加载状态。

如果图片没有依赖加载尺寸进行布局，则不要无意义 setData。

### 7.3 图片错误状态

单张图片错误时，只更新该图片状态。

不要：

- 过滤并重建整个图片数组
- 重新提取所有图片
- 重新生成题干模型
- 让其他图片重新加载

### 7.4 图片尺寸和内存

检查是否一次性渲染过多原图。

对于一道题的少量图片可直接加载，但如题目可能包含大量高分辨率图片，请评估：

- 是否需要 `lazy-load`
- 是否设置合理容器宽度
- 是否存在同时渲染上一题、当前题、下一题全部原图
- 预取逻辑是否导致多题图片同时驻留内存

不要降低当前题图片清晰度来掩盖内存问题。

### 7.5 preview 数据

`wx.previewImage` 的 urls 不应在每次点击时重新执行复杂扫描。

可在题目变化时提前准备有效预览 URL 数组。

```text
miniprogram/utils/question-runner-adapter.js
```

检查以下函数及等价实现：

- 图片 URL 标准化
- 图片提取

- 图片去重
- blank option groups 提取

# ================================================== 十二、审计状态竞态

重点检查：

### 12.1 快速连续点击

连续点击：

```text
I → II → III
```

最终状态必须为 III，不能被异步旧更新覆盖。

### 12.2 点击后立即切题

用户点击选项后立即下一题：

- 当前题答案应正确保存。
- 上一题异步 setData 不得写入下一题。
- 图片错误或加载回调不得污染下一题。

### 12.3 observer 与页面更新竞态

确认是否存在：

```text
组件本地乐观更新
父页面旧 answerMap 下发
observer 覆盖本地状态
父页面新 answerMap 再下发
```

导致闪烁、点击无反馈或状态反复。

应建立单一明确的答案真源，并保证乐观反馈与最终状态一致。

### 12.4 缓存恢复竞态

接口返回和本地缓存恢复同时发生时：

- 不得相互覆盖较新的答案。
- 应有明确的合并优先级。
- 不得重复初始化 quiz-runner。

# ================================================== 十六、修复优先级

按以下优先级处理：

### P0：必须修复

- 无限循环
- observer 循环触发
- 主线程明显长时间阻塞
- 同步死循环
- 页面永久 loading
- 请求锁无法释放
- 快速点击导致答案错误
- 页面卸载后持续高频 setData
- 定时器泄漏
- 一次点击触发切题或重复提交

### P1：上线前修复

- 点击时大范围 setData
- 每次点击同步写大缓存
- 图片重复加载
- observer 重复解析题干和图片
- 请求乱序覆盖
- 多次重复事件
- wx:key 不稳定导致节点重建
- 高频日志
- touchmove 高频 setData

### P2：建议优化

- 可合并的小数组遍历
- 非关键路径中的轻微重复计算
- 可读性较差但暂不影响性能的状态逻辑

不要把所有风格问题都标记为性能问题。
